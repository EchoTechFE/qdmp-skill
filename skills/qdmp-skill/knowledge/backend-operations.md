# 后端服务操作详情

## 云服务使用规范

本规范适用于千岛小程序的代码生成、数据建模、接口联调、故障排查、数据验收和代码 Review，也适用于生成的脚本、定时任务及自动重试逻辑。用户提出“验收全量点位数据”“逐条核对”“检查所有图片”等需求时，同样必须执行本规范。

### 1. 禁止将媒体文件内容存入千岛云数据库

- 图片、视频、音频及其他大文件必须使用支持该文件类型的 OSS / 对象存储；千岛云数据库只保存资源 ID、持久访问地址及必要元数据（如文件名、类型、大小、宽高、时长）。图片和视频按 [OSS 上传流程](./api-guide.md#oss-图片与视频上传流程post) 接入；其他类型先确认存储能力，不猜测上传接口。
- 禁止将文件二进制、Buffer、Blob、Base64、Data URL 或字节数组写入数据库；禁止通过压缩、转字符串、拆分字段 / 文档 / 集合、GridFS 等方式变相存储媒体内容。缩略图、封面和生成结果图片同样适用。
- 不得以“临时缓存”“上传失败兜底”“文件较小”为由将媒体内容落库。上传能力缺失或上传失败时，返回明确状态，保留必要任务元数据；不能退回数据库存文件。
- 校验实际写入值，不能仅凭字段名为 `url` 或类型为 `string` 判定合规。媒体地址字段不接受 `data:` 或本地 `blob:` 地址；不持久化上传签名、临时上传凭据作为资源地址。千岛 OSS 已发布媒体使用查询结果中的 `cdnUrl`。
- 数据模型和写入接口都要遵守上述边界，包括更新、批量导入、缓存、任务记录及数据库日志。后端校验媒体字段，避免将含文件内容的完整请求体或上游响应直接落库。

### 2. 禁止反复调用不存在的云服务接口

频繁请求不存在的接口可能触发 WAF 封禁，导致调用方 IP 被封。开发者和 Agent 必须在请求前核实接口，并在失败后停止无效流量。

#### 调用前确认

- 平台接口依据当前 API 文档 / Swagger 确认；自建云服务接口依据后端路由和目标环境的实际部署版本确认。核对域名、环境、路径前缀、版本、HTTP 方法和参数。
- 未找到接口依据、接口尚未实现或尚未部署到目标环境时，先补齐实现 / 部署或确认文档，禁止靠猜路径、枚举版本、切换方法或批量探测来寻找接口。
- 健康检查只能调用已确认存在的检查接口；不得假定 `/health`、`/ping` 或根路径存在。仅检查本地进程监听状态时可使用端口检查，不能把它当作云端业务接口可用的证据。

#### 失败后的停止条件

| 情况 | 必须执行的处理 |
| ---- | -------------- |
| HTTP 404、405，或业务响应明确提示接口 / 路由不存在 | 立即停止该请求的自动重试、轮询和定时触发，先核对路由、方法、环境与部署状态；不能换一组猜测路径继续请求。 |
| 文档明确表示业务对象不存在的 404 | 按业务空态或对象失效处理，不自动重试；不能仅凭 404 认定整个接口不存在。 |
| HTTP 403、429 或明确的 WAF 拦截 / IP 封禁提示 | 停止相关自动请求并检查响应原因。403 可能是权限问题，429 可能是限流或配额问题，不能一律认定为 WAF；已明确 WAF 拦截时停止向受影响服务继续探测。 |
| 超时、网络错误或 5xx | 仅对已确认存在且允许安全重试的接口使用有上限的退避重试；写入结果不明时先查状态，不能盲目重放。 |

- 停止必须覆盖请求库重试器、页面生命周期、定时器、后台任务及并发调用方，避免单次请求已报错但后台仍持续发送。同一失败接口的重复触发应合并或阻断；页面退出、任务取消时清理轮询。
- 临时限流须遵守服务端 `Retry-After`（若提供）；只有原因明确且允许恢复时才恢复有界请求。配额耗尽、权限错误、接口不存在或 WAF 封禁不能靠等待后无限重试解决。
- 排查保留脱敏后的请求方法、路径、目标环境、HTTP 状态、业务码、`requestId` 和发生时间，优先查代码、部署状态和服务日志。修正配置 / 部署或确认限制解除后，先单次验证，再恢复正常调用。
- 禁止通过换 IP、代理、域名或并发客户端绕过 WAF 封禁。无法自行恢复时，将诊断信息交给平台支持处理，不继续探测解封状态。

### 3. 全量数据验收的请求控制

- “全量”“尽快”“逐点验收”表示覆盖范围和交付要求，不表示允许并发压测或快速扫描。先确认验收字段、数据总量及已有批量 / 分页接口，优先复用已有响应；不要为每个点位重复请求同一份数据或同一张图片。
- 未取得目标服务明确的限额时，验收任务默认使用一个共享串行队列，**并发数为 1，相邻请求启动时间至少间隔 1000ms**。分页、详情、图片检查、结果写入及重试均经过该队列；不能用 `Promise.all`、多进程、多个 Agent 或多套定时器分摊后绕过总限速。串行但无等待或仅等待几十 / 几百毫秒也不符合此默认规则。
- 上述数值是本 Skill 的保守默认值，不是平台承诺的安全 QPS。已知服务限额更严格时遵守更严格值；只有取得明确限额依据并核算整体请求量后才能调整，不能凭“暂无报错”自动提速。
- 执行前设置并记录本次最大请求数和时间预算，所有重试也计入预算。规模未知时，先用受限的单次分页请求确认总量，再估算完整验收开销；仍无法估算时设置有限预算分批处理。达到预算立即停止并保留断点，不能自动追加预算、重启任务或从第一页重扫来继续消耗请求。
- 分页检查重复游标和重复 ID；遇到接口不存在、权限 / 限流错误或 WAF 信号时，按上一节停止条件停止队列中尚未发出的请求，包括其他点位 ID 对同一路由的调用。不要仅让失败的那个点位退出，其他点位继续请求。
- 验收结果记录总量、已检查、失败、未检查和停止原因；预算耗尽或中断时明确报告“未完成全量验收”及续跑断点，不将抽样结果冒充全量完成。保存验收结果、失败现场和缩略图信息时仍只写必要元数据，不保存图片正文、完整响应或含媒体内容的错误信息。

### 4. 生成与 Review 检查

- 数据模型及所有写入路径是否只保存媒体引用和必要元数据？是否存在 Base64、二进制或拆分文件内容落库？
- 每个云服务请求是否有文档或已部署路由依据，方法、环境和前缀是否一致？
- 404 / 405 / 接口不存在时是否停止重试、轮询和其他重复触发？是否区分业务对象不存在？
- 限流、权限错误和 WAF 拦截是否按原因处理？暂时性失败的重试是否有上限，写入请求是否避免重复执行？
- 全量验收是否使用共享限速队列并设置请求数 / 时间预算？默认请求间隔是否至少 1000ms？停止后是否保留断点并如实报告未检查范围？

发现违规实现时，先修正存储方案或请求触发逻辑，再继续联调；不要通过继续请求线上服务来验证已知违规行为。

## 通用子流程: 读取项目配置

先按 [项目形态与范围](./project-workflows.md#step-1-判断项目形态与部署范围) 确定本次操作。新 create 默认获取带空主配置的全栈模板，CLI 保留内容并设置 0600 权限与忽略规则；没有主配置的历史纯前端仍直接读取实际 qdmp.json，不要求 AppSecret、Go 或数据库。主配置存在时，日常命令直接优先使用其公开字段，前端副本中的旧 AppID 不触发手动同步前置；主配置损坏或所选环境身份缺失不能回退。

范围包含后端时，读取真实根 qdmp-config.json 的 appId/runtime/environment、后端 variables 和可选 MongoDB；上传/发布还需真实 AppSecret。CLI 可从根目录或 backend/ 定位同一文件，显式 --config 只读取指定文件。实际前端源码可在根目录，也可在 frontend/；不为读取配置搬动项目。

### 一次性初始化与旧项目升级

- 历史纯前端需要添加后端时，在项目根目录执行 `qdmp backend init --runtime go`，从同一 qdmp-taro-template 仓库临时提取后端；只在主配置缺失时，从实际 qdmp.json 一次性继承 appId/devAppId/loader/name/latest，并保全 AppSecret、MongoDB、variables 等已支持的旧后端字段。
- 已有主配置逐字保留，不以新的前端副本覆盖；这不是长期双向同步。新增主配置为 0600 并忽略提交。
- 已有 backend/ 但缺少主配置时，用 `qdmp config init --json` 无损补齐，不删除后端。直接克隆当前官方模板已带空主配置，无需补齐。
- build 内部生成/同步公开 qdmp.json，打包直接读取主配置。config sync 仅是可选的本地兼容文件更新工具，不是日常调用的必经步骤。

完整字段契约见 [初始化与配置](./backend-production.md#初始化与配置)。MongoDB 省略/null/uri 与 database 双空时未启用，部分填写错误；启用后 database=AppID。variables 是后端 JSON 对象，不转为 process.env，不导入前端；生产配置改变后重新打包，不能复用旧 configSha256。

**关键变量**：

- projectRoot：本次项目根目录；sourceDir：其 backend/。
- frontendDir：实际根式或分离的前端目录，由 CLI 定位。
- mongoUri/mongoDatabase：本地主配置中完整启用的数据库配置，不猜测主机或凭据。

## 通用子流程: 保护敏感配置

业务项目的 `qdmp-config.json` 可含 AppSecret 与数据库密码，不能提交已填写的配置或将文件放入上传包；官方模板仓库仅跟踪所有凭据为空的初始文件。create 会移除模板 .git 并保留忽略规则，生成项目中的主配置未被跟踪。生产运行所需字段仅由打包器注入私有副本，发布包和镜像均按秘密制品保护：

- 确保 `{projectRoot}/.gitignore` 存在且包含一行 `qdmp-config.json`；不存在则创建，已存在但缺该行则追加。
- **后端打包**：稳定 Go 模板只使用 `qdmp backend package`，检查排除配置、密钥和本地目录；源文件中的配置保持为空。生成的秘密 ZIP 及镜像按受保护制品处理，不能提交仓库。
- **前端打包**：在识别出的实际前端目录执行 `qdmp build` / `qdmp-cli upload`。分离结构的主配置位于上级；根式纯前端工程也不能把后端秘密配置放进源码或产物。构建前排除/隔离误放的敏感配置，不要求纯前端补建该文件。
- `frontend/qdmp.json` 只投影 appId/devAppId/loader 等公开白名单，不含 AppSecret、MongoDB、variables 或 runtime，可正常提交；未知主配置字段保留原文件，不自动导入前端或保证后端注入。

## 通用子流程: 本地文件打包上传（publish/diff 共用）

稳定 Go 模板统一执行 [构建并冻结发布包](./backend-production.md#构建并冻结发布包)：

```bash
qdmp backend package --json
qdmp backend upload --archive <本次ZIP> --sha256 <本次SHA256> --version temp-diff --json
```

从 package 结果读取路径、归档 SHA-256 和 manifest 的 configSha256；生产配置改变后重新打包，不能复用旧包。审查 `qdmp_gitlab_diff(ref="master", version="temp-diff")` 后，用同一归档、同一 SHA-256 上传正式版本。禁止手工 `zip -r`、两次上传之间重新打包、从项目 MCP 配置猜上传主机，或在 curl 参数暴露 AppSecret。HTTP 上传端点和成功判定见 [归档上传](../references/backend-mcp.md#归档上传)。

已有 Node.js / Python 后端不受新的 Go 模板打包器支持。保留其已验证工程和平台工具，使用该工程受控的打包与配置流程；没有可验证流程时停止并说明缺口，不临时退回通用 ZIP 或声称通过 Go 单入口门禁。

## 通用子流程: Pipeline 状态跟踪（publish/rollback 共用）

`qdmp_gitlab_pipeline_status` 在成功时会更新日志并自动合并分支，具有写入副作用。对已授权的发布或回滚，默认间隔 10 秒、最多 60 次跟踪；失败读取本次 `pipeline_logs`，超时保留版本和制品摘要，不重放 publish。

CLI deploy 成功仅返回 Pipeline 事实和 acceptance_required，不自动调用 Aliyun/K8s。Agent 继续使用宿主 MCP 收集实际部署版本、Job/副本和生产日志，并验证真实健康接口。成功判定按 [上线验收](./backend-production.md#上线验收与失败处理)：build 与 deploy Job 成功、两个新副本 Ready、再次查询的运行版本匹配，且已实现的健康和就绪接口通过。总状态 success、镜像 tag 或单个旧副本响应均不能单独证明上线完成。

## 通用子流程: Schema 代码生成（操作 7 / 后端代码变更共用）

`qdmp-schema.json` 是业务数据定义来源；修改前先读已有后端 README、配置加载和数据库入口，复用真实 API，不重复创建另一套数据库连接。

1. 有持久化需求时，确认本地 `qdmp-config.json` 已配置 MongoDB；生产数据库名等于 AppID。缺少凭据时由用户在本地安全填写，不要求在聊天中提供密码。
2. 模型接收模板已初始化的数据库对象或业务仓储接口；不要从模型直接读取主配置，也不要将 URI、密码或 AppSecret 写入源码常量。现有 Node.js / Python 项目使用其环境注入契约，同样禁止源码硬编码。
3. Go 平台只编译 `main.go`。新模型放进明确导入的 package，接入真实启动和路由调用；不要依靠同目录额外 `init.go` 或仅 `go build .` 成功。保留模板生产配置和就绪检查，新增必需索引初始化失败时不能报 ready。
4. 根据 Schema 创建必要索引，记录迁移影响；禁止仅因 Schema 未列出就自动删除线上已有索引、集合或数据。破坏性变更先生成可审查迁移计划，按已有授权执行。
5. 只存媒体引用与必要元数据，后端校验所有写入路径；业务重试和批量导入也遵守 [云服务使用规范](#云服务使用规范)。
6. 运行针对性模型检查和 `go test ./...`，再用 `qdmp backend package --json` 验证单入口构建。生成后报告实际新增/修改模型、索引与接入点，不展示配置值。

本地调试通过进程环境或项目已有受保护配置切换，禁止自动重写源码里的生产数据库地址；正式打包重新读取生产配置，不依赖把测试地址替换回去。

## 操作 1: publish（发版）

读取配置、实际 runtime 和本次用户授权。稳定 Go 后端完整执行 [稳定后端模板与正式发布](./backend-production.md) 的构建、冻结、diff、正式上传、publish、master 合并及上线验收；工具参数见 [MCP 清单](../references/backend-mcp.md)。

用户已明确授权当前范围的正式发布时，可生成说明并选择未占用的 patch 版本（无历史版本默认 v1.0.0，最新 v1.2.3 则默认 v1.2.4），展示具体目标、版本、制品摘要和 diff 后连续执行；用户已指定版本则使用该版本并验证唯一性。仅分析、创建模板或打包不等于授权生产发布；缺少授权时在可审查结果上取得一次决定，不强制每一步重复问版本和确认。

发布前检查最新 Pipeline，未结束时禁止并发。镜像构建或推送开始后版本不可复用，失败修复使用新 patch。不要直接 push master、手工覆盖平台 CI / Dockerfile 或跳过打包器。运行时不符、配置不完整、异常 diff、构建失败或验收证据不足时停止并报告具体状态。

只有全部验收通过才能报告“后端发版成功”，包含实际版本、归档 SHA-256、Pipeline/Job、两个 Ready、运行版本及健康结果。全量部署也只有此时才继续前端。

**Step 1**: 读取项目配置

**Step 2**: 并行调用
- `qdmp_gitlab_list_versions(appId, appSecret)`
- `qdmp_k8s_deployed_version(appId, appSecret)` → 标注 `◀ 部署镜像版本`，健康状态另行验收

**Step 3**: 格式化展示
```
版本历史

  v1.2.4  2026-03-11  部署成功
  新增用户个人资料页面

  v1.2.3  2026-03-05  部署成功  ◀ 运行中
  修复商品列表翻页时闪白问题
```

**Step 4**: 可选查看详情 → 调用 `qdmp_gitlab_get_version(appId, appSecret, version)`

## 操作 3: rollback（版本回滚）

**Step 1**: 读取项目配置

**Step 2**: 调用 `qdmp_k8s_deployed_version` 展示当前版本

**Step 3**: 调用 `qdmp_gitlab_list_versions`，AskUserQuestion 让用户选择目标版本（排除当前版本）

**Step 4**: 明确展示 `vX.Y.Z → vA.B.C`；目标和回滚授权已有明确证据时直接继续，缺少决定时在此取得一次确认

**Step 5**: 调用 `qdmp_gitlab_rollback(appId, appSecret, version)`

**Step 6**: 执行"Pipeline 状态跟踪"子流程

**Step 1**: 读取项目配置

**Step 2**: 调用 `qdmp_k8s_deployed_version` 展示当前版本

**Step 3**: AskUserQuestion 选择日志类型和时间范围

日志类型：
```yaml
options:
  - label: "启动/运行日志 (Recommended)"
    description: "查看实例启动和运行时的输出日志，适合排查启动失败"

```

**字段类型说明**：
- `type: "string"` - 普通文本
- `type: "string[]"` - 文本数组
- `type: "string[]", "format": "oss-url"` - OSS 文件地址数组（图片、视频、文件等），通过千岛开放平台 openapi 上传后获得的地址
- `type: "number"` - 数字
- `type: "date"` - 日期时间
- `type: "ref"` - 关联其他对象，通过 `refKey` 指定关联字段（不使用 ObjectId）

**唯一标识字段**：
- 每个对象必须有 `uniqueKey` 指定唯一标识字段
- 唯一标识字段必须设置 `unique: true`
- 可以设置 `auto: "uuid"` 自动生成，或由用户提供
- 用户对象的 `openId` 必须取自 `/auth/v1/token` 的 `AUTHORIZATION_CODE` 成功响应 `data.openId`，不自动生成；**禁止从 `user.me`（`GET /user/v1/me`）获取、兜底或将其 `id` 转换为 `openId`**。

每个对象自动加入 `createdAt`、`updatedAt`（`auto: true`），无需用户指定。

**索引识别规则**：

根据字段角色自动推导索引，无需用户指定：

| 字段特征 | 索引类型 | 示例 |
|---|---|---|
| `uniqueKey` 字段 | 唯一索引 | `productId`, `openId` |
| `type: "ref"` 字段 | 普通索引 | `createdBy` |
| `createdAt` | 普通索引（倒序） | 列表分页排序 |

在追问阶段通过以下问题识别复合索引和额外索引：

1. **"这个对象最常按什么条件查列表？"** → 高频过滤字段 + `createdAt` 组成复合索引
2. **"是否经常看某个用户/某个上级对象下的数据？"** → 确认 ref 字段索引
3. **"哪些字段必须全局唯一？"** → 额外唯一索引

常见复合索引模式：
- 某用户的对象列表：`(createdBy, status, createdAt)`
- 分类筛选列表：`(category, status, createdAt)`
- 某对象下的子列表：`(productId, createdAt)`

**索引合并规则**：收集所有候选索引后，对单字段索引做裁剪：
- 若已有复合索引以该字段开头，则单字段索引可省略（最左前缀覆盖）
- `unique: true` 的索引无论如何保留（唯一约束语义不可替代）

例如：拟生成的候选索引已有 `(createdBy, status, createdAt)` 时，可从候选定义中省略 `createdBy` 单字段索引；`productId` 唯一索引保留。此规则只整理生成计划，不删除数据库现有索引。

**不建索引**：低区分度字段（布尔、2-3个枚举值）单独建索引、很少作为查询条件的字段。

**索引命名规范**：
- 格式：`idx_{字段简写}[_uniq]` 或 `idx_{关键词}_{hash6}`
- 全小写，下划线分隔
- 单字段：`idx_product_id`, `idx_created_at`
- 复合索引：`idx_user_status_time`（取关键词，不完整拼接字段名）
- 唯一索引可选加 `_uniq` 后缀
- 长度不超过 64 字符
- 冲突处理：若关键词重名但字段定义不同，追加 6 位哈希后缀（如 `idx_user_status_a1b2c3`），哈希来源为索引定义的规范化字符串（字段+方向+unique）

**索引检查与显式迁移**：

1. 读取数据库已有索引并与本次 Schema 对比，生成可审查的变更计划；首次创建必要索引必须受启动/部署流程控制并具备有界超时。
2. Schema 未列出的线上索引继续保留；同名但字段、方向或唯一性不同的索引标记为迁移冲突，禁止启动时自动 drop / 重建。
3. 删除、替换索引或变更唯一约束前，核对已有数据、查询影响、回退方案和用户授权，通过独立显式迁移执行；不能将“重新设计模型”当作删除线上索引的授权。
4. 唯一约束和业务正确性必需索引创建或验证失败时，启动失败或保持 `/readyz` 未就绪，禁止仅打印 warning 后接流量。可选性能索引的失败可按经过审查的降级策略处理，不能冒充完整验收。
5. 记录脱敏后的迁移版本、索引名称、成功或失败状态；不在日志中输出连接串、完整业务数据或凭据。

在 `qdmp-schema.json` 中用 `indexes` 字段记录：
```json
"Product": {
  "indexes": [
    { "name": "idx_product_id_uniq", "fields": { "productId": 1 }, "unique": true },
    { "name": "idx_created_at", "fields": { "createdAt": -1 } },
    { "name": "idx_user_status_time", "fields": { "createdBy": 1, "status": 1, "createdAt": -1 } }
  ]
}
```
