# PRD 归档与迭代

## 项目内的固定入口

- 每个小程序以 `{projectRoot}/doc/prd.md` 作为 PRD 入口与产品共用约束的来源。默认只需这一份。确有独立业务域、单份难以维护时，在 `doc/` 下保留最多两份稳定的专题文件 `prd-<domain>.md`，由入口链接并标明负责的业务域。共计 1–3 份有效 PRD，按业务域划分，不按迭代、日期、版本号或任务划分。
- 延续已有模块和可引用的小节标题；新功能、规则调整和验收差异更新到对应章节。同一项要求由一处维护，其余位置只链接。`doc/prd.md` 保留跨域要求、产品范围、角色和专题索引。版本变化可在各文件顶部或变更摘要里记录，过去版本由 Git 或归档保留。
- 优先读取入口与本次相关的专题。发布验收和数据建模也沿入口链接查找本次范围内的模块。设计稿、接口约定、测试方案等独立文档不计入 PRD 数量。

## 盘点历史版本

1. 确认当前小程序根目录。首次为旧项目维护 PRD、显式要求收敛、没有入口，或发现多个版本与路径时，执行完整盘点。已盘点且只有一个清晰入口时，本轮小改可直接读取入口和相关专题。运维、只读和明确跳过 PRD 的任务不顺带搬迁文件。
2. 用 `node <实际 qdmp-skill 目录>/scripts/prd-inventory.mjs --cwd <项目根目录>` 只读列出候选、跳过项和不可读目录。候选包含根 `PRD.md`、`doc/`、`docs/`、`frontend/` 下按 PRD、产品需求等命名的历史文件，以及 `prd/` 目录中的文档。脚本不可用时，用 Glob/Grep 或 `rg --files` 在同一范围内盘点，不依赖 `qdmp-cli` 版本。用户点名、现有文档引用或标题可确认是 PRD 的非标准文件名也纳入。归档、构建、依赖、样例和其他小程序不参与自动收敛；遇到读取失败、符号链接或含糊路径时单独报告，不能据此判断没有旧 PRD。入口 `doc/` 或目标文件若是符号链接，先核对实际位置与项目范围再决定写入。常规扫描优先读标题或开头判定，名称不是移除文件的证据。
3. 把候选区分为现行需求、被替代的迭代、草稿、专题、旧路径跳转和其他资料。多份旧稿或跨业务域时优先按模块分派子 Agent。先只读盘点，给出「来源路径与章节、确认依据、冲突、独有内容、引用」，再按下文分工压缩。扫描器只返回路径与大小，文档是否有效由 Agent 阅读内容和引用判断。
4. 兼容旧路径。只有历史 PRD 时，使用已识别的历史内容继续本次任务；只有确认没有有效输入时，才走新建或代码反向生成。仅需读取时可直接引用已识别的旧文档。首次建立规范入口或本次确实要更新 PRD 时，复用这些内容，无需重新描述已有需求。对仓库级的一次性收敛，明确要求整理时执行下方步骤；普通开发只做本次所需的 PRD 编辑，如发现旧稿过多则列出建议整理范围，不擅自移动无关文档。

## 合并与归档

1. **确定每个模块的有效需求。** 用用户最新明确确认、审批记录或文档中的明确替代关系辨认生效项。版本号、文件时间、文件名和 Git 提交时间只辅助排序。当前代码用于核对已实现行为；需求与实现不一致时分别记录，不能把当前代码当作用户已经接受删改需求的证据。没有证据的矛盾放进入口的「待确认问题」，写明各来源和影响，避免把任一方案写成已确认规则。只在冲突影响本次功能或验收时向用户确认这一项，其余模块照常合并。
2. **按现行业务语义压缩。** 去掉重复背景、过程性讨论、旧方案、重复示例和已经在设计稿、API、数据字典或测试文档维护的细节，必要时链接对应章节。为每个模块保留角色、权限、边界、正常与异常流程、关键状态、数据可见性、验收和待确认问题。保留业务阈值、默认值和兼容例外。将可追溯来源集中到对应模块或简短索引，避免逐句复制旧稿。先压缩一份，只有独立业务域确实适合按需读取时才拆成专题。
3. **分派压缩和归档。** 多份或跨域时，优先让子 Agent 按业务域返回压缩草稿与「旧要求 → 新章节」映射，或写到主 Agent 指定的互不重叠文件。主 Agent 合并共用规则、确认冲突并核对候选清单。新 PRD 写入并逐条验收后，可将已核定的移动或删除清单委派给一个有文件工具权限的子 Agent；指定源、目标、兼容入口和回退方式，一次只处理明确文件。禁止让多个 Agent 同时改同一路径或自行扩大删除范围。缺少子 Agent 或所需工具时由主 Agent 执行同样流程。
4. **确认替代关系后处理旧文件。** 收敛会覆盖旧入口或专题时，先保存可验证的原件或明确的 Git 版本并记录去向，再写入新内容。确认已替代的独立旧稿移到 `doc/archive/prd/<原项目相对路径>`。检查归档内容、相对附件链接和原路径引用；同名不同内容保留独立原件。默认使用可恢复的移动。只有已验证归档有同一原件（内容相同），仓库引用已修复或旧入口已兼容，且明确包含清理范围时，才移除多余源副本。永久删除唯一历史原件须有用户明确授权。文件存在未提交编辑、归属不明、不可读、未知外链或机器读取依赖时保留原件并说明。旧工具消费正文或固定锚点时保留原兼容能力，不能仅以短链接替换；确认只需导航时可留旧锚点及跳转。
5. **验证体积和完整性。** 对收敛范围内原有的有效 Markdown（含 `.markdown` / `.mdx`）和新有效 PRD 分别汇报总 UTF-8 字节与各输出大小。归档、跳转和非 Markdown 原件单列，不能用它们抵消主文档增长。默认以入口约 16 KiB、每份专题约 24 KiB 为建议复查线，用户或项目可另定。总量未下降或单份超过复查线时，先去重、缩短过程叙述和改用引用，再判断是否按业务域拆分。必留规则较多或原件从非 Markdown 转入时，说明体积变化的原因，不能只以文件数减少报告已压缩。对照映射检查每条有效需求、例外与待确认问题都有落点，入口、专题、旧路径及附件可访问，报告每份旧稿去向。同一输入重复执行应复用归档和入口。
