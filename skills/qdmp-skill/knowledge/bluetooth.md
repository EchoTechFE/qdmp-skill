# BLE 中心设备工作流

先按 [事实查询流程](./api-discovery.md) 在 Bridge provider 确认本次所需的适配器、扫描、连接、GATT、读写、通知、MTU、配对与清理能力。接口目录、参数、事件字段、平台差异及二进制类型全部来自 MCP；缺失任一必要阶段时说明缺口，不从历史表格恢复方法。

## 调用流程

1. 核实目标平台能力与系统权限，再初始化。先注册发现/连接监听，再开始扫描或连接，发现结果去重。
2. 设备、服务和特征身份来自真实发现结果；连接后重新获取服务/特征，按可读、可写和通知能力选择操作，不复用旧连接的对象。
3. 读取前先监听结果；通知先注册回调再启用。写入完成与设备协议回复分别等待，不能把写请求完成视为业务完成。
4. 二进制转换、字节序、包长与串行分包按已确认契约和设备协议处理。MTU 协商失败时记录实际限制，不承诺固定包长或跨端一致。
5. 页面退出停止扫描、关闭通知、解绑当前回调并断开连接。断线后清空会话状态，重连重新发现，不自动重放写请求。配对和系统设置只在需求需要且能力已确认时执行。

## 诊断与验证

保留无设备、重复发现、连接失败、断线、特征不支持、读写异常、通知先后顺序、分包串行、MTU 失败和页面清理用例。注册与解绑使用同一回调；检查并发状态不会串设备或串特征。用真实设备验证协议回复、系统授权和各目标端行为，mock 通过不等于硬件联调成功。
