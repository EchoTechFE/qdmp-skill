# Go 业务 API 优化与兼容性

设计、实现或审查 QDMP Go 业务 API 时，先确认调用方、鉴权、数据量上限、常用筛选与排序、首屏实际需要的字段，以及一次请求可承担的查询和下游调用次数。可增长的列表和搜索从第一版设计分页，固定且有明确小上限的枚举可一次返回。先限制工作量、减少查询、核对索引。只在本次业务有明确需求时引入缓存、并发或预计算。通用规则见 [业务 API 优化与兼容性](./api-optimization.md)。

沿用项目现有路由、驱动和数据层。正式打包按[后端运行契约](./backend-production.md)验证真实构建入口。默认 Go 模板的构建命令是 `go build main.go`，新增代码须由该入口实际编译进发布产物。开发和验收调用平台 OpenAPI 时遵循[云服务限速和停止条件](./backend-operations.md#云服务使用规范)。本指南的业务接口示例用于自有 API，平台 OpenAPI 的参数和分页规则以已确认的真实契约为准。

## 列表和搜索分页

- 新的持续滚动列表优先使用游标分页。与前端约定 `limit` 的默认值和最大值，例如 20 和 50，按响应体积及业务体验调整。这些是项目配置示例。服务端校验整数、上下界、游标大小和格式，非法参数沿用项目的 4xx 错误格式。客户端视游标为不透明字符串。
- 用稳定业务排序加唯一键断开并列。例如 MongoDB 按 `(createdAt DESC, _id DESC)`，下一页的查询在原筛选与权限条件下限制为 `createdAt < t`，或 `createdAt = t 且 _id < id`。比较字段方向与实际排序一致，优先使用不可变排序字段。查询 `limit + 1` 条判断是否有下一页，最多返回 `limit` 条，并用本页最后一条生成 `nextCursor`。约定末页信号，例如 `nextCursor: null`。只有页面确实依赖总数时才单独计算，避免每页重复 `count`。 [MongoDB 稳定排序与范围分页](https://www.mongodb.com/docs/manual/reference/method/cursor.skip/#using-range-queries)
- 每页重新检查会话与访问范围，把用户、应用和可见性约束放入数据库筛选。校验游标与当前排序、筛选和访问范围匹配。需要防篡改时签名或用服务器持有的状态标识游标。游标不授予权限，内容不含令牌或敏感字段。条件改变时从第一页开始。
- 游标可减少深页扫描和因记录插入导致的偏移漂移。若排序值会变化或业务要求跨页一致快照，明确处理并发写入的语义，按需求采用固定边界或快照方案。已支持页码跳转、总数或 `page/pageSize` 的接口保持该契约，必要时限制新增调用的深页或另加游标入口，先验证旧客户端。

## 查询、批量与索引

- 把过滤、排序、投影和条数限制下推到数据库。列表只读响应所需字段，图片正文、大字段和详情按需获取。Go MongoDB 驱动游标应检查迭代错误并关闭。只有结果已有小上限时才一次解码全部。
- 一页列表关联名称、状态等小数据时，优先按缺失 ID 去重并批量查询，再在内存中匹配，保留列表的原有顺序、权限过滤和缺失项语义。批量接口也要限制 ID 数和负载，逐项核对访问权限。若上游只有逐项请求，先遵守实际限额和延迟预算；确需并行时设并发上限并随请求取消，避免用无界 goroutine 掩盖 N+1。
- 索引从实际查询出发。例如按 `ownerId` 和 `status` 等值过滤，再按 `createdAt` 和 `_id` 倒序翻页，可在数据样本上验证 `{ ownerId: 1, status: 1, createdAt: -1, _id: -1 }`。若 `status` 可选，另检查没有该条件时的排序是否仍由合适的索引支撑。用具备代表性的筛选、数据分布和深页执行计划验证扫描文档数、返回数和排序阶段。索引有写入和存储成本，按[数据建模的索引迁移规则](./backend-operations.md#操作-7-schema数据建模)对照现有索引，不自动删除或替换线上索引。 [MongoDB 复合索引 ESR 指南](https://www.mongodb.com/docs/manual/tutorial/equality-sort-range-guideline/)
- 每个进程复用已初始化的 MongoDB Client 和 HTTP Client，按服务生命周期关闭连接。连接池上限结合实例数、等待时间和后端容量确定，避免按请求创建客户端。 [MongoDB Go 驱动连接池](https://www.mongodb.com/docs/drivers/go/current/connect/connection-options/connection-pools/) · [Go net/http Client](https://pkg.go.dev/net/http#Client)

## 超时、恢复与缓存

- 在 Go HTTP handler 使用 `r.Context()`，把同一请求上下文传给业务层、MongoDB 或 `http.NewRequestWithContext`。为依赖调用按交互延迟预算派生 `context.WithTimeout` 并及时 `cancel`，父请求断开时让工作结束。保留服务端读取头部、空闲连接和请求体大小的限制，调整写超时时按真实响应模式和网关超时做回归。 [Go 请求取消](https://go.dev/doc/database/cancel-operations) · [Go net/http Server](https://pkg.go.dev/net/http#Server) · [MongoDB Go 驱动的上下文](https://www.mongodb.com/docs/drivers/go/current/context/)
- 默认让调用错误尽快返回。确需重试时在同一时间预算内，仅按契约重试可安全重复的短暂失败，限制次数并遵循上游退避。写入超时可能已经提交，优先查询结果或使用业务幂等键，登录 code 不自动重放。权限、路由错误、限流和 WAF 走[云服务处理规则](./backend-operations.md#云服务使用规范)。
- 只有调用链确有重复查询且允许短时陈旧时才引入缓存。优先缓存共享、可容忍短暂陈旧的读数据，声明 TTL、容量、写后失效及失败回退。若确需缓存私有结果，缓存键隔离应用、用户和权限范围，并包含查询条件及数据版本，读取仍须校验当前访问权限。跳过登录、鉴权错误及包含敏感会话数据的响应缓存。线上多副本的进程内缓存各自独立，需要写后立即可见的业务用数据库一致性方案。Redis 等共享缓存只有在确有重复请求瓶颈及部署条件时引入。

## 旧业务变更与验证

- 开始改动前记录现有 method/path、请求参数、状态和业务码、响应结构、排序、权限、会话和数据归属。旧调用方继续得到原契约。例如旧路由返回完整数组，给新版客户端增加新的分页路由或参数模式，原调用不传参数时保持原行为。在保留真实旧流量的前提下，再分阶段迁移和下线旧入口。需要更换身份主键或索引约束时走独立的数据迁移。
- 按改动范围验证空页、末页、多条相同排序值的记录、超限或非法 `limit`、错误游标、换筛选或用户、取消请求和依赖超时。并发写入时按声明的一致性验证漏项与重项。旧接口使用真实旧请求样例回归，新接口接至少一次前端翻页，确认取消或重复请求不会影响新页状态。
- 验证改动后的业务行为并运行 `go test ./...`，涉及正式构建时用 `qdmp-cli backend package --json` 验证打包。常规开发无需性能基线、压测、基准测试或 profiling。
