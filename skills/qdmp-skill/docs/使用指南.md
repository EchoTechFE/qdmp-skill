# 千岛小程序 Skill 使用指南

## 概述

千岛小程序 Skill 是一个帮助开发者快速创建、开发和部署千岛小程序的 Claude Code 技能。它提供了完整的开发流程支持，从环境配置到最终部署发布。

## 前置条件

1. 注册 [千岛开放平台](https://open.qiandao.com) 账号，创建小程序获取 `appId`；包含后端时再安全填写 `appSecret`
2. 安装 [Node.js](https://nodejs.org)，qdmp-cli 支持 `^22.12.0 || ^24.11.0 || >=26.0.0`
3. 安装 Claude Code

## 一、环境配置

### 1. 安装开发工具

```bash
# 安装 pnpm
npm install -g pnpm

# 安装 qdmp-cli
npm install -g qdmp-cli

# 验证安装
qdmp-cli --version
pnpm --version
```

### 2. 添加 MCP 服务

```bash
claude mcp add --transport http qdmp-gitlab https://openapi.qiandao.com/gitlab/mcp
claude mcp add --transport http qdmp-aliyun https://openapi.qiandao.com/aliyun/mcp
```

### 3. 安装 Skill

```bash
# 添加插件市场
/plugin marketplace add https://github.com/EchoTechFE/qdmp-skill.git

# 安装插件
/plugin install qdmp-skill
```

## 二、快速开始

启动 Claude Code 后，使用 `/qdmp-skill` 触发千岛小程序开发助手。

### 创建项目

```
创建一个千岛小程序项目，项目名叫 myShop
```

新创建直接执行 `qdmp create myShop`，或保留显式 `-t default`。CLI 从 `git@github.com:EchoTechFE/qdmp-taro-template.git` 单次获取完整全栈模板，校验 frontend/backend 及自带的空 qdmp-config.json，保留主配置内容，只设置 0600 权限和忽略规则；不增加后端选项、不搬模板目录或拼装第二个模板。克隆流程移除模板 .git，因此生成项目中的主配置未被跟踪。官方模板仓库只提交 AppID、AppSecret、MongoDB 字段为空、variables 为 {} 的配置，不提交实际凭据；直接 git clone 也已有主配置，无需 config init。规则见 [稳定后端模板](../knowledge/backend-production.md)。

已有项目根目录存在 `qdmp.json` 时必须先迁移前端：同级无 `backend/` 为旧纯前端，有该目录为旧全栈，即使后端为空也不改判。先执行 `qdmp config migrate --check --json` 生成只读计划，再执行 `qdmp config migrate --json`，将旧前端工程移入 `frontend/`、提取根 `qdmp-config.json`，并完成 EMP 前端规范。原后端语言和业务保留，不强制 Go，也不因前端迁移改写后端。顶层结果只描述目录/前端迁移，`backendReadiness` 单独记录后端的 ready/pending/unsupported/not_applicable；后端待处理不阻断前端操作。只有本次需要后端打包部署时，才接入相应 runtime 的入口、配置和发布契约。纯前端保持无 `backend/`，不要求 AppSecret、Go 或数据库。详细规则见 [旧项目强制迁移](../knowledge/project-workflows.md#旧项目强制迁移)。

上游全栈布局必须先合并，再发布对应 CLI。当前模板改动在研发分支准备审查，不能声称主分支已支持；旧 HEAD 布局不符时应停止，不临时拼装。

项目结构：

```
myShop/
├── frontend/
│   ├── src/
│   │   ├── pages/        # 页面
│   │   ├── components/   # 组件
│   │   ├── composables/  # 组合式函数
│   │   └── utils/        # 工具函数
│   ├── package.json
│   └── qdmp.json         # 小程序配置（appId、loader 等非敏感配置）
├── backend/              # CLI 稳定 Go 生产模板，监听 :8080
└── qdmp-config.json      # 权威主配置（身份、runtime、MongoDB、后端variables；敏感，需忽略提交）
```

所有新版项目均有根主配置与 `frontend/`，全栈另有 `backend/`。日常命令直接优先使用主配置中的公开字段，不要求先 config sync；build 内部更新 Taro/EMP 需要的 `frontend/qdmp.json`，sync 只是可选本地工具。主配置坏或所选环境身份缺失不能回退旧前端身份；已有编译产物身份不属于主配置对应环境的有效身份映射时重新 build，不能只改 ZIP。秘密和后端 variables 不导入前端；MongoDB 省略/null/双空时无持久化，部分填写错误，后端配置变化需重新打包。规则见 [配置优先级](../knowledge/backend-production.md#配置优先级与前端兼容)。

### 开发调试

**全量调试（推荐）**：

```
部署测试环境
```

Claude 会先完成旧项目迁移，再按项目范围启动服务；全栈先验证本地后端，再启动前端 dev server，不自动改写前端地址。默认模板从公开 AppID 推导正式后端域名，登录示例仍需已部署的正式后端；已有项目按其实际本地代理配置联调。原生 `pnpm dev` 前，先在根目录执行 `qdmp config sync --json` 导出公开字段，再进入 `frontend/`。

```
本地测试环境已就绪

  前端 dev server: http://localhost:10086
  后端 API:        http://localhost:8080
```

**单独调试**：

```
部署后端测试环境    # 仅启动后端
部署前端测试环境    # 仅启动前端 dev server
```

**真机调试**：

```bash
qdmp build
qdmp-cli upload -d "真机调试版本"
# 使用千岛 App 扫码预览
```

### 发布上线

Agent 先完成旧项目识别与强制迁移：纯前端需要根主配置和 `frontend/`，只执行前端步骤，无需 AppSecret、Go 或数据库；全栈先后端再前端。小程序不存在纯后端项目；只有后端而无前端时报告结构不完整，有 `backend/` 但实现或配置缺失时报告待完善，不能降级为纯前端。

```
部署上线
```

以下工具链仅针对全栈范围：Agent 完成针对性业务测试并生成具体说明，执行 `qdmp backend deploy --description "<说明>" --json`，由 CLI 按 `go` / `nodejs22` 构建当前最新代码、内部生成并校验生产归档和摘要、自动选择新 patch，再通过 [后端 MCP](../references/backend-mcp.md) 直接发布并跟踪正式 master 合并。默认无需单独 package、传递摘要、查看 diff 或两次 deploy；用户需要审计时才加 `--review`，按 [可选 diff 审查](../knowledge/backend-production.md#可选-diff-审查) 继续。Node 运行 `npm ci`、可选 build 和入口校验，生产变量仅写入私有 `.qdmp-runtime-config.json`；Go 使用单入口构建与私有配置嵌入。远端 runtime 必须与归档相同，不能自动重建已有仓库。命令只返回 Pipeline 事实和 acceptance_required，不自动查询 Aliyun/K8s；Agent 查询实际版本、Job/副本及日志，并验证真实健康/就绪接口（默认模板为 `/healthz`、`/readyz`）。全部通过后，核对前端使用的 `https://{appId}.qiandaomp.com` 并继续上传；默认模板由公开 AppID 推导地址，只有旧项目存在实际地址配置时才按其契约修改。Pipeline success 或镜像 tag 单独不足。已授权的正式发布连续执行；初始化、分析、打包不会自动上线。生产流程不依赖浏览器。

前端 `upload` 成功只表示上传版本。正式上线还需将真实版本设为体验版并提审；当前 CLI 支持 `qdmp review --version <实际版本号> --auto-publish --json`，由平台在审核通过后自动发布。提审成功不代表已上线，最终状态以平台结果为准。发布规则、可选 diff 审查和验收由 Skill 维护，Agent 编排；CLI 执行，MCP/API 服务由平台提供。

修复或开发完成后，Agent 在本地检查通过并报告结果后主动询问是否继续真机测试、是否部署涉及服务。用户已经明确要求部署（包括“修改后部署”）时，直接构建当前工作区最新代码，自动生成版本描述、选择下一未占用 patch，并连续执行部署和验收，不再要求用户选择或再次确认版本。只有缺配置、构建失败、目标不明确，或可选审查发现异常差异时才报告具体阻塞。

## 四、常见问题

### qdmp-cli 命令未找到

```bash
npm install -g qdmp-cli
```

如果仍然找不到，检查 npm 全局路径是否在 PATH 中：
```bash
npm config get prefix
# 确保 {prefix}/bin 在 PATH 中
```

### 依赖安装失败

先运行 `node --version`，核对[前置条件](#前置条件)中的 CLI 运行时范围。Node 20 不再受支持；保留旧纯前端项目源码，不代表旧 Node 仍可运行新版 CLI。运行时不兼容时使用已选择的受支持 Node 环境，不自动更换用户全局 Node，也不通过跳过安装脚本或编译检查绕过错误。

确认网络正常，可尝试：
```bash
pnpm install --registry https://registry.npmmirror.com
```

### 登录失败

1. 检查网络连接
2. 在支持输入的前台交互终端中执行目标 `qdmp` 命令
3. 在 CLI 提供的扫码登录、手动登录 URL、账号密码登录三种方式中任选一种
4. 登录完成后 CLI 会自动继续原命令；也可以执行 `qdmp getMe` 验证

Agent 对话使用 `qdmp login --agent --env prod`（开发环境为 `dev`），Agent 会展示浏览器登录链接和二维码图片，保持进程直到登录完成。详细流程见 [Agent 对话登录](../knowledge/agent-login.md)。无人值守的 CI 请设置 `QDMP_TOKEN`。不要在聊天中发送账号或密码。
